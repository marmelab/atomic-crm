## Business Knowledge

- (Sealed 2026-09, commit `41faa70c`) Scholarship Pricing + Capacity — scholarship is a **pricing mode** of an existing Offer (`deals.pricing_mode`/`offer_payment_options.pricing_mode` = `standard`|`scholarship`), never a second Offer, a separate pipeline, or a Stripe coupon. **Locked prices**: The Living Example $3,000 (Pay in Full, or 3×$1,000), Growing Yourself Up $700 (Pay in Full, or 2×$350) — standard Financial Need plans are excluded from scholarship Deals by construction (options are scoped by `pricing_mode`, never by a second ad hoc flag). **Reservation rule**: a scholarship slot is reserved the instant Leif grants it (Deal-held, unpaid, no TTL — release is an explicit human action, never automatic), stays held through onboarding/active/offboarding once Won, and releases only when the resulting Enrollment reaches `completed`; a backward lifecycle correction off of `completed` reclaims the slot only if it's still free, otherwise the correction itself is rejected — never silently displacing another holder. **Authoritative DB model**: one `scholarship_slots` row per Offer (ordinary `id` PK + `unique(offer_id)` — deliberately NOT `offer_id` itself as the PK, since every other resource in this app assumes a plain `id` column), `holder_deal_id` XOR `holder_enrollment_id` (a `CHECK` makes "both populated" structurally impossible), claimed via a race-safe `INSERT ... ON CONFLICT (offer_id) DO UPDATE ... WHERE both-null` — Postgres's own row-lock serializes two genuinely concurrent grant attempts for the same Offer, proven against the real linked project. The Deal→Enrollment holder handoff on Won happens inside the same trigger execution that creates the Enrollment (`handle_deal_won()`), so no other transaction can ever observe the slot as free in between. Append-only `scholarship_slot_events` records every grant/release/conversion/reclaim. **Payment/Offer Page**: `pricing_mode` freezes immutable the instant a Deal reaches Won; a stale payment option is cleared in the same write that changes `pricing_mode` (found via real-infrastructure testing — granting/releasing while a now-mismatched option was still selected used to fail outright); Stripe Checkout Sessions stamp `pricing_mode` into their own metadata at creation, and `stripe_webhook` refuses to mark Won on a mismatch — a reactive backstop that holds even if the best-effort proactive Checkout-invalidation call (`stripe_invalidate_checkout`) fails; the public Offer Page and `stripe_checkout` scope payment options by `pricing_mode` server-side, so the browser is never the authority for amount or option selection. **UI, human-acceptance-repaired**: the Opportunity lightbox's Scholarship control was originally a full-width card — Leif's own reaction was that this made scholarship look like a normal, everyday step — so it's now one quiet line (small badge + a link-styled grant/release action) in the same compact metadata row as Source/Entry path/Payment option; "Potential Value" is kept in sync with the frozen commercial terms on grant/release (previously showed stale/$0 — the dedicated grant/release action bypasses the edit form's own amount-sync effect); a small "Outstanding Scholarship Reservations" Dashboard card surfaces unpaid, held-open reservations; a new "Open Offer Page" action was added to the lightbox (the personalized Offer Page route had no discoverable authenticated-UI path at all before this slice — a pre-existing gap, not something scholarship broke). **Human acceptance**: two real Stripe test-mode purchases were human-completed end to end — Living Example scholarship Pay-in-Full ($3,000 once) and Living Example scholarship 3×$1,000 installments (the resulting Subscription/Schedule directly verified in the Stripe test dashboard: $1,000/month, `total_installments=3`, upcoming $1,000 invoice, explicit subscription end date consistent with exactly 3 total payments) — both correctly transitioned Committed→Won→Enrollment(onboarding), transferred the scholarship slot atomically, and left the paid Offer Page as a non-purchasable confirmation; a competing grant attempt was rejected, live, while the slot was held, with zero side effects. All disposable `ZZTEST-SCHOL-*`/`ZZTEST-STRIPE-*`/`ZZTEST-INSTALL` fixtures (7 contacts, 7 deals, 3 enrollments and all dependent onboarding/offboarding items, Tasks, and event rows) were removed by exact provenance after acceptance — every test Enrollment was first advanced through its real, authoritative lifecycle to `completed` so any scholarship slot it held was released the legitimate way, never a direct column hack; both LE and GYU scholarship slots verified free and structurally valid afterward; Porsche Brown (contact 8), Sarah Henke (contact 9), contact 17/Enrollment 7, and all 39 real Year Planning windows confirmed untouched. **Outstanding debt, explicitly outside this slice**: clean-room migration/restore proof is still a separate project-wide go-live requirement, not closed by this slice; Supabase Pro/backups and production auth/domain config remain outstanding before real client data; **a Stripe TEST `sk_test_` secret Leif previously exposed in a screenshot still needs rotation before final Stripe closure/go-live** (deliberately not rotated during this slice to avoid derailing the seal); ordinary Living Example/Growing Yourself Up capacity (`max_active_clients`/Cohort capacity) remains advisory-only outside Scholarship's own hard-enforced capacity, unless separately hardened later.

## Instagram Intake — Approved Architecture (blocked on Meta Developer registration, see checklist above)

Audited and approved 2026-09; not yet implemented. Preserve these decisions across sessions so a future resume doesn't have to re-litigate them:

- **Business rule, structurally enforced, not just policy:** an Instagram DM is never automatically a Contact/Opportunity/Application/Waitlist entry. AI (later phase) or passive echo-observation may only produce a *suggestion*; only an explicit Leif action changes durable sales state — mirrors how `reviewApplication.ts` already makes "an unreviewed Application can't silently become approved" structurally impossible, not merely documented.
- **New entities, separate from Contact:** `instagram_participants` (keyed by the stable Instagram-Scoped ID/IGSID — never the mutable username), `instagram_conversations`, `instagram_conversation_messages` (Meta message ID for idempotency, direction, `is_echo`, text, raw payload). Same durable-current-state + append-only-history shape this codebase already uses twice (`deals`/`deal_stage_events`, `sales_calls`/`sales_call_events`).
- **Identity:** IGSID is the only stable match key; username is display-only (Instagram usernames are user-changeable). No auto-merge into an existing Contact by name — linking to a real Contact happens only via the existing email-match-on-Application-submit path, or an explicit Leif-driven manual link.
- **Native Instagram stays Leif's primary conversation surface.** The CRM observes and remembers; it does not need to become the sending interface. An outbound `is_echo` message (Leif replying/sending from the native app) IS reliably observable via webhook with full text (confirmed from official Meta docs) and may surface a suggestion (e.g. "looks like you sent Jane the LE application — track as an LE prospect?") — never silently create state on its own.
- **Lead Source vs Entry Path already exist and are already correctly separate** — `deals.source` already has an `'instagram'` value, `deals.entry_path` already has `'instagram_conversation'`, both currently unused/manual-only. Reuse these, don't reinvent them.
- **DNE precedent to extend, not reinvent:** `doNotEngageGuard.ts`'s existing rule (block *new* sales-state creation for a DNE contact; don't hide/block anything else) is the model — a DNE-linked conversation stays visible, but never gets promoted into a new Deal/Application.
- **Collaboration inquiries (v1):** a lightweight `review_collaboration` Task type (task types have no DB constraint — pure app-config, same pattern as `sales_call_cancelled`). No separate collaboration entity/pipeline.
- **Retention:** 12 months post-inactivity is the current product direction for raw message content, but no destructive deletion automation until a later privacy/hardening slice — Phase 1 only needs a schema field capable of tracking inactivity (e.g. `last_activity_at`), not the deletion logic itself.
- **Phase 1 scope (ingestion only):** Meta app/Instagram Login connection, webhook endpoint + signature verification (same HMAC-SHA256 pattern as `acuitySignature.ts`), the three new tables, stable-identity handling, inbound/outbound/`is_echo` capture, Meta-message-ID idempotency, a minimal read-only proof surface. Explicitly NOT in Phase 1: AI classification, any Contact/Opportunity/Application/Waitlist mutation, collaboration automation, outbound CRM sending, capacity recommendations, an inbox UI.
- **Meta platform facts to build against** (official docs, 2026-09): Instagram API *with Instagram Login* (not Facebook Login) needs no linked Facebook Page; for a single business managing only its own account under Standard Access, official Meta docs state App Review is "Not required"; Conversations API can only retrieve the 20 most recent messages per conversation (no real history backfill — must capture going forward via webhook, there is no later fallback); the 24-hour standard messaging window and 7-day Human Agent tag extension apply to Instagram, not just Messenger.
