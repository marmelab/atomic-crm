## Business Knowledge

- Core resources: contacts, companies, deals (Kanban pipeline), tasks, notes, tags, and sales (team members).
- Domain options (genders, sectors, deal stages/categories, note statuses, task types) are `<CRM>` props in `src/App.tsx`, not hardcoded.
- Sales users sync with Supabase `auth.users` via triggers; deletion is unsupported — accounts are disabled instead.
- Aggregated reads use database views (`contacts_summary`, `companies_summary`), which FakeRest emulates in the frontend.
- Two interchangeable data providers: Supabase (production) and FakeRest (in-browser demo, resets on reload).
- Filters use `ra-data-postgrest` syntax (`field_name@operator`); operators must be supported by the FakeRest `supabaseAdapter`.

## Instagram Intake — Approved Architecture (blocked on Meta Developer registration, see checklist above)

Audited and approved 2026-09; not yet implemented. Preserve these decisions across sessions so a future resume doesn't have to re-litigate them:

- **Business rule, structurally enforced, not just policy:** an Instagram DM is never automatically a Contact/Opportunity/Application/Waitlist entry. AI (later phase) or passive echo-observation may only produce a *suggestion*; only an explicit Leif action changes durable sales state — mirrors how `reviewApplication.ts` already makes "an unreviewed Application can't silently become approved" structurally impossible, not merely documented.
- **New entities, separate from Contact:** `instagram_participants` (keyed by the stable Instagram-Scoped ID/IGSID — never the mutable username), `instagram_conversations`, `instagram_conversation_messages` (Meta message ID for idempotency, direction, `is_echo`, text, raw payload). Same durable-current-state + append-only-history shape this codebase already uses twice (`deals`/`deal_stage_events`, `sales_calls`/`sales_call_events`).
- **Identity:** IGSID is the only stable match key; username is display-only (Instagram usernames are user-changeable). No auto-merge into an existing Contact by name — linking to a real Contact happens only via the existing email-match-on-Application-submit path, or an explicit Leif-driven manual link.
- **Native Instagram stays Leif's primary conversation surface.** The CRM observes and remembers; it does not need to become the sending interface. An outbound `is_echo` message (Leif replying/sending from the native app) IS reliably observable via webhook with full text (confirmed from official Meta docs) and may surface a suggestion (e.g. "looks like you sent Jane the LE application — track as an LE prospect?") — never silently create state on its own.
- **Lead Source vs Entry Path already exist and are already correctly separate** — `deals.source` already has an `'instagram'` value, `deals.entry_path` already has `'instagram_conversation'`, both currently unused/manual-only. Reuse these, don't reinvent them.
- **DNE precedent to extend, not reinvent:** `doNotEngageGuard.ts`'s existing rule (block *new* sales-state creation for a DNE contact; don't hide/block anything else) is the model — a DNE-linked conversation stays visible, but never gets promoted into a new Deal/Application.
- **Collaboration inquiries (v1):** a lightweight `review_collaboration` Task type (task types have no DB constraint — pure app-config, same pattern as `sales_call_cancelled`). No separate collaboration entity/pipeline.
- **Retention:** 12 months post-inactivity is the current product direction for raw message content, but no destructive deletion automation until a later privacy/hardening slice — Phase 1 only needs a schema field capable of tracking inactivity (e.g. `last_activity_at`), not the deletion logic itself.
- **Phase 1 scope (ingestion only):** Meta app/Instagram Login connection, webhook endpoint + signature verification (same HMAC-SHA256 pattern as `acuitySignature.ts`), the three new tables, stable-identity handling, inbound/outbound/`is_echo` capture, Meta-message-ID idempotency, a minimal read-only proof surface. Explicitly NOT in Phase 1: AI classification, any Contact/Opportunity/Application/Waitlist mutation, collaboration automation, outbound CRM sending, capacity recommendations, an inbox UI.
- **Meta platform facts to build against** (official docs, 2026-09): Instagram API *with Instagram Login* (not Facebook Login) needs no linked Facebook Page; for a single business managing only its own account under Standard Access, official Meta docs state App Review is "Not required"; Conversations API can only retrieve the 20 most recent messages per conversation (no real history backfill — must capture going forward via webhook, there is no later fallback); the 24-hour standard messaging window and 7-day Human Agent tag extension apply to Instagram, not just Messenger.

## Contracts + Onboarding — confirmed next slice, NOT yet implemented (architecture review required first)

Identified 2026-09 during Stripe Slice B's own human acceptance: a person must not appear to "disappear" from view the moment their Deal reaches Won. Preserve this conceptual model across sessions so a future resume doesn't have to re-derive it:

- **Two distinct lifecycles, deliberately not merged.** Sales: `Committed → payment succeeds → Won` — Won stays the terminal Pipeline event, full stop. Client delivery (separate, downstream): `Won → Enrollment(status=onboarding) → Active → Offboarding → Completed`.
- **Do NOT add Onboarding (or any fulfillment state) as a Pipeline/Deal stage.** That would corrupt sales-funnel/stage analytics by mixing fulfillment states into it — Won must stay a clean, unambiguous terminal sales event. Fulfillment status lives on `enrollments.status` (already exists), not on `deals.stage`.
- **The real gap is operational visibility, not data modeling** — `enrollments` and its `onboarding` status already exist (the `handle_deal_won()` trigger already creates them); nothing currently surfaces them as a work queue. The next slice needs to make `Enrollment(status=onboarding)` an obvious, actionable queue, at minimum: clear Dashboard visibility that someone has just paid and needs onboarding; direct navigation from that Dashboard item to the person's onboarding work; payment context visible (offer, amount/payment plan, first payment received — reuse the Offer Page's own "first payment received, not plan paid in full" distinction); a contract task/status; required access/permissions tasks/status; offer-specific onboarding requirements (distinct checklists for Living Example vs. Growing Yourself Up); an explicit, deliberate transition from Onboarding → Active once required onboarding is complete.
- **Contract itself is post-payment**, not part of the Stripe slice — confirmed explicitly when Stripe Slice A was scoped.
- Architecture review is required before implementation begins on this slice — do not start building it speculatively.
