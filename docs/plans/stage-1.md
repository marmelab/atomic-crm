# Этап 1. Ядро и дизайн — план

Источник: TZ.md, раздел 11, этап 1. Правила: docs/PRODUCT_RULES.md.

**Готово, когда:** два бизнеса (UA и PL) видят только свои данные; у каждого свои валюта и реквизиты.

## Решения (согласовано 2026-11-13)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Один человек в нескольких бизнесах | Да, переключатель бизнеса вверху |
| 2 | Страна ЕС | Польша |
| 3 | Роли | Заводим все 6 (владелец, менеджер, специалист, кладовщик, бухгалтер, партнёр). Сразу работают: бухгалтер — только чтение; настройки и участников меняет только владелец. Остальные права — вместе с модулями |
| 4 | Меню | Сегодня (стартовый экран) + Продажи (контакты, компании, сделки). Чаты, Закупки, Деньги скрыты до появления модулей |
| 5 | Демо-данные | Отдельный бизнес «Демо», удаляется целиком одной операцией |
| 6 | Демо-режим без базы (FakeRest) | Не поддерживаем |
| 7 | Языки | Украинский и английский; французский убираем |
| 8 | Команда агентов | Не используем, Claude делает сам по шагам |
| 9 | Git | Локальные коммиты в ветке `stage-1`; отправка в GitHub — только после проверки этапа и с разрешения |

## Как устроена изоляция бизнесов

- Таблица `businesses`: название, страна, валюта, часовой пояс, язык, вид бизнеса, реквизиты.
- Таблица `members`: кто в каком бизнесе и с какой ролью.
- У каждого человека есть «текущий бизнес». Функция базы `current_business_id()` возвращает его, только если человек действительно участник этого бизнеса.
- У каждой таблицы колонка `business_id`. Значение по умолчанию — текущий бизнес, поэтому интерфейсу не нужно его подставлять.
- Политики RLS: читать и менять можно только строки текущего бизнеса. Переключение бизнеса = смена «текущего» + перезагрузка данных.
- Все внешние ключи на `businesses` с `on delete cascade`: удаление бизнеса удаляет все его данные.
- Ограничение: в двух вкладках одновременно нельзя держать разные бизнесы (в обеих будет последний выбранный).

## Шаги

Каждый шаг заканчивается локальным коммитом в `stage-1` и короткой проверкой, которую может сделать владелец.

### 1.1. Бизнесы, участники, изоляция данных
- Таблицы `businesses`, `members`, роли; `current_business_id()`, `has_role()`.
- `business_id` + RLS для: companies, contacts, contact_notes, deals, deal_notes, tasks, tags, configuration (настройки становятся у каждого бизнеса свои).
- Представления (`contacts_summary`, `companies_summary`, `activity_log`), поиск, объединение контактов, триггеры — учитывают бизнес.
- Файлы-вложения: путь начинается с id бизнеса, доступ только своему бизнесу.
- Регистрация: открыта для всех, каждый новый пользователь попадает в мастер создания бизнеса (сам мастер — шаг 1.4; до него — временное автосоздание бизнеса).
- Серверные функции (приглашение сотрудников, входящая почта, MCP-сервер) работают в пределах бизнеса.
- Бизнес «Демо»: демо-данные из `seed.sql` переносятся в него.
- Функция удаления бизнеса (только владелец).
- Тесты базы (pgTAP, `npx supabase test db`): для каждой таблицы — чужой бизнес не видит, не создаёт, не меняет, не удаляет.
- **Проверка:** зарегистрировать второго пользователя — он не видит демо-контактов.

**Сделано (2026-11-13):** миграция `20261113120000_businesses.sql`, схема (`01`, `02`, `04`–`06`, новый `09_businesses.sql`), 69 тестов изоляции в `supabase/tests/database/businesses.test.sql`.
Отличия от плана:
- Файлы-вложения перенесены на этап 5 «Документы»: хранилище пока общедоступное со случайными именами файлов; закрытие доступа требует временных ссылок, которые ТЗ относит к модулю документов.
- В Atomic CRM не было демо-данных в базе (только в режиме без базы), поэтому бизнес «Демо» заполняется новыми примерами в `seed.sql`. Первый зарегистрированный пользователь становится его владельцем и ответственным за записи.
- Защита аккаунтов: почту, имя и аватар меняет только сам человек; «отключить» действует только внутри бизнеса; у бизнеса всегда остаётся хотя бы один активный владелец.
- Ссылки между записями (контакт → компания, заметка → контакт, сделка → контакты, метки) не могут вести в другой бизнес.
- Минимальный переключатель бизнеса — в меню пользователя (полноценный — на шаге 1.6).

### 1.2. Страновые пакеты как данные
- Таблицы `country_packs`, `tax_rates` (даты начала и конца), `requisite_fields` (поля реквизитов, обязательность, правило проверки), `numbering_rules`.
- Пакет UA: язык uk, валюта UAH, Europe/Kyiv; ЄДРПОУ (8 цифр, контрольная сумма), ІПН (10 цифр, контрольная сумма), IBAN UA; ПДВ 20 / 7 / 0 %.
- Пакет PL: язык pl→en (польского интерфейса пока нет), валюта PLN, Europe/Warsaw; NIP (контрольная сумма), REGON (9/14 цифр, контрольная сумма), IBAN PL; VAT 23 / 8 / 5 / 0 %.
- Проверка реквизитов — в базе (реквизиты не сохранятся с ошибкой) и на экране (подсказка сразу).
- Блок RU/BY: таких пакетов нет, страна RU/BY и IBAN RU/BY отклоняются базой.
- **Проверка:** в базе видно два пакета; неверный NIP не сохраняется.

**Сделано (2026-11-13):** миграция `20261113130000_country_packs.sql`, схема `10_country_packs.sql`, проверки реквизитов на TypeScript (`src/components/atomic-crm/requisites/validators.ts`) и в базе (`requisite_is_valid`) по одним правилам, 25 + 30 тестов.
Отличия от плана:
- Украина: добавлена ставка ПДВ 14 % (отдельные сельхозтовары), всего 20 / 14 / 7 / 0 %.
- Ставки действуют в продукте с 2026-01-01; перед первым настоящим документом их должен подтвердить бухгалтер каждой страны.
- Реквизиты Украины: нужен ЄДРПОУ (компания) или ІПН (ФОП) — «хотя бы одно из группы». Польша: обязателен NIP.
- Обязательность база не навязывает при сохранении (её проверит мастер на шаге 1.4 через `missing_requisites`), а неверные значения не сохраняет никогда.
- Нумерация документов: шаблоны есть (UA `{YYYY}-{NNNN}`, PL `FV/{NNNN}/{MM}/{YYYY}`), используются с этапа 4.
- Бизнес «Демо» — украинский, с реквизитами.

### 1.3. Деньги и валюты
- У бизнеса — базовая валюта из пакета. У сделок — `currency` (ISO 4217) рядом с суммой в минимальных единицах.
- Таблица `fx_rates` (пустая, заполняется на этапе 7).
- Единая функция показа денег по стране: `12 400 ₴`, `12 400 zł`.
- **Проверка:** сумма сделки в UA-бизнесе показана в гривнах, в PL — в злотых.

**Сделано (2026-11-14):** миграция `20261113140000_money.sql`, схема `11_money.sql`, `src/components/atomic-crm/money/` (formatMoney, toMinor, fromMinor, MoneyInput), 14 + 5 тестов.
Отличия от плана:
- У бизнеса также часовой пояс (по умолчанию из пакета) — понадобится экрану «Сегодня».
- Валюта сделки пока всегда равна валюте бизнеса (выбора в форме нет): итоги по колонкам и графикам считаются без курсов. Сделки в других валютах — вместе с курсами на этапе 7.
- Выбор валюты убран из настроек CRM; базовую валюту задаёт мастер (шаг 1.4).
- Исправлена страница настроек (после 1.1 не открывала настройки бизнеса).
- Тесты интерфейса, проверявшие мобильный вид через подмену модуля, переведены на реальный размер окна: подмена ненадёжно срабатывала при полном прогоне.

### 1.4. Мастер настройки
- После регистрации: название, страна (UA или PL), вид бизнеса (услуги, торговля, производство и опт, B2B-услуги), реквизиты по пакету с проверкой «на лету». Валюта, часовой пояс и язык подставляются сами.
- Настройки бизнеса (владелец): реквизиты, участники и роли, удаление бизнеса с вводом названия для подтверждения.
- **Проверка:** пройти мастер за UA и за PL.

**Сделано (2026-11-14):** миграция `20261114100000_business_setup.sql`, схема `12_business_setup.sql`, `src/components/atomic-crm/business/` (SetupPage, BusinessSettingsPage, RequisiteFields), 6 + 4 теста.
- Новый пользователь без приглашения больше не получает «My business»: сайт ведёт его в мастер (`/setup`). Приглашённые попадают в бизнес пригласившего; первый пользователь локальной базы по-прежнему получает «Демо».
- Мастер: название, страна (карточки UA / PL с валютой), вид бизнеса (4 шаблона), реквизиты с подсказкой при неверных контрольных цифрах; кнопка неактивна, пока не хватает обязательных.
- Страница «Бизнес» (`/business`, только владелец): название и реквизиты, люди и роли (`set_member`), доступ к бизнесу, удаление с вводом названия.
- В меню пользователя: «Бизнес» и «Добавить бизнес».
- Исправлены ещё два места, сломанные на 1.1: поиск сделок по категории и перезагрузка после смены бизнеса.

### 1.5. Украинский язык
- Перевод всех текстов интерфейса на украинский; французский удаляется.
- Переключатель UA / EN в профиле; язык по умолчанию — из пакета.
- **Проверка:** весь интерфейс на украинском, без английских «хвостов».

### 1.6. Новый вид (перед началом — скилл frontend-design)
- Экран «Сегодня» — стартовый: новые сообщения (пока пусто — блок скрыт), дела на сегодня (задачи), что ждёт решения (просроченные задачи).
- Меню: Сегодня, Продажи; скрытые модули не показываются. Настройки — в профиле. Переключатель бизнеса.
- Кнопка «+»: контакт, компания, сделка, задача. Ctrl+K — быстрый поиск и создание.
- Один акцентный цвет, контраст WCAG AA, светлая и тёмная темы, сначала телефон.
- Пустые разделы — с кнопкой первого действия.
- **Проверка:** с телефона (узкое окно) всё делается одной рукой.

### 1.7. Проверка этапа
- Автотест (Playwright): регистрируются владелец UA и владелец PL, проходят мастер, создают контакт и сделку; каждый видит только своё, валюта и реквизиты свои.
- Ручная проверка во встроенном браузере, затем — проверка владельцем.
- После одобрения владельца — вопрос о разрешении и `git push` ветки `stage-1`.

## Риски
- Шаг 1.1 трогает почти все таблицы и серверные функции Atomic CRM — это самый большой и рискованный шаг; делается первым, с тестами.
- Будущие обновления из marmelab/atomic-crm будет сложнее подтягивать: схема базы заметно расходится.
